# ADR 0009: Alert confirmation, persisted baselines, sequence cursor and routing

- Status: Accepted
- Date: 2026-10-27

## Context

v0.4 (ADR 0008) detects anomalies and raises alerts, but the first smoke runs showed four problems that made the alerts hard to trust and to operate:

- **Noise.** The iperf3 schedule starts and stops a flow every 15 s with rates between 1 and 8 Mbit/s. Each step is a real deviation from an EWMA baseline, so `rx_bps`/`tx_bps` alerts opened on almost every round: 25 throughput alerts in about nine minutes, with up to six alerts open at once, all resolving on their own a minute later. The absolute floors that could quiet them (`min_bps_delta`, the sigma floors) were `DetectionConfig` defaults with no setting.
- **Cursor race.** The live feed picked up changed alerts by `updated_at > cursor`. `now()` is fixed at transaction start, so a row committed after the API's poll but stamped earlier than the cursor was skipped until its next change. The window was milliseconds, but a resolved alert that never changes again would be missing from the feed for good.
- **Memory-only baselines.** A collector restart re-entered the one-minute warm-up and lost the baseline of any anomaly still active, so it was re-detected only once the baseline had settled on the anomalous level.
- **Unrouted webhook.** A single `NETPULSE_COLLECTOR_ALERT_WEBHOOK_URL` received every event kind, `refreshed` and `suppressed` included, with no way to send critical alerts to one destination and drop-rate alerts to another. The `alerts` table also grew without bound.

## Decision

**Alerts open only after consecutive signals.** `AlertPolicy.open_after_signals` (default 3, 15 s at 5 s polling) adds a `pending` status to the lifecycle in `netpulse_core.alerts`. The first signal for a key creates a pending state with `signals = 1` and emits nothing; each consecutive signal increments the count and raises the pending severity to the strongest seen; the alert opens, as one `opened` event, when the count reaches the policy. A cycle without a signal discards the pending state, so the count never accumulates across gaps. `opened_at` is the time of the first signal, not of the confirmation, so the row tells when the anomaly started; the pending `signals` count stays inside the state and is not part of the webhook payload, which keeps the v0.4 contract. A 30 s `host_down` fault yields six `drop_rate` samples and still opens; a 10 s iperf3 burst yields two throughput samples and never does. `open_after_signals = 1` restores the v0.4 behaviour.

**The floors are settings and `min_bps_delta` is 1 Mbit/s.** `min_bps_delta`, `min_sigma_bps`, `min_sigma_rate`, `drop_rate_floor` and `error_rate_floor` are `NETPULSE_COLLECTOR_DETECTION_*` settings mapped by Compose from `COLLECTOR_DETECTION_*`. The collector default for `min_bps_delta` is 1 Mbit/s (the core default stays 100 kbit/s), which ignores the smaller iperf3 steps outright; the confirmation above covers the larger ones. The z thresholds and the rate floors keep their v0.4 values, so `drop_rate` and `error_rate` guards are unchanged.

**The feed cursor is a monotonic sequence assigned in commit order.** The migration adds `alerts.seq bigint NOT NULL DEFAULT nextval('alerts_seq')` with a unique index; every collector write (`opened` upsert, `refreshed`, `escalated`, `resolved`) and the first acknowledgement set `seq = nextval('alerts_seq')`, and the API fetches `seq > cursor ORDER BY seq` (at most 500 rows per cycle) and advances the cursor to the highest `seq` it returned. A sequence alone does not fix the race: a collector transaction could take `seq = N`, an acknowledgement could take and commit `N + 1`, the broadcaster could move its cursor past `N`, and the collector's row would commit unseen. Every writer therefore takes `pg_advisory_xact_lock(hashtext('alerts_seq'))` as the first statement of its transaction, both in the collector's cycle apply and in the API's acknowledge, so sequence values are handed out in commit order and no row ever commits with a `seq` below a cursor that has already passed it. Integration tests observe the second writer waiting in `pg_locks`. The broadcaster's cursor starts as `None` and is set from the first open snapshot, so an empty table at startup does not replay history; the `opened` upsert consumes two sequence values on conflict, which the cursor tolerates because it only compares.

**Baselines are persisted every cycle and reloaded at startup.** The `alert_baselines` table keys `(dpid, port_no, metric)` with `mean`, `variance`, `samples` and `updated_at`, with the same range checks as `port_stats`. The detector reports which baselines changed in a cycle and the observer upserts exactly those in one `executemany` (32 rows per cycle for the eight physical ports and four metrics). At startup the collector loads every row and logs the count; a row that fails validation discards the whole load and the collector warms up as before instead of scoring on garbage. When a port is absent for 60 cycles the detector forgets its samples, baselines and alert states: its open alerts are resolved and notified, pending states are dropped, and its baseline rows are deleted; a failed delete is kept as pending and retried on the next cycle, unless the port reappears first.

**Routing is pure in core and the collector owns the transport.** `netpulse_core.routing` defines `AlertRoute(name, webhook_url, min_severity, metrics, kinds)` and `route_events(events, routes)`, which returns, per route, the events whose kind is in the route's `kinds`, whose severity is at least `min_severity` and whose metric is in `metrics` when a list is given. `kinds` defaults to `opened`, `escalated` and `resolved`; `refreshed` and `suppressed` leave the collector only when a route lists them. Empty `metrics` or `kinds` lists are rejected at parse time rather than silently matching nothing, and `webhook_url` is validated as an HTTP URL. `NETPULSE_COLLECTOR_ALERT_ROUTES` is a JSON array of routes; `NETPULSE_COLLECTOR_ALERT_WEBHOOK_URL` still works and becomes a route named `default` ahead of the configured ones. Malformed routes stop the collector at startup. The collector shares one httpx2 client across one `WebhookAlertNotifier` per route with a URL and logs the events of routes without one; `RoutingAlertNotifier` fans each cycle's events out, and a failing route never blocks the next.

**Resolved alerts are purged.** The observer deletes resolved alerts older than `NETPULSE_COLLECTOR_ALERT_RETENTION_DAYS` (7) once every `NETPULSE_COLLECTOR_ALERT_RETENTION_EVERY_CYCLES` (720, one hour at 5 s polling) and logs the count. Open alerts are never touched. The purge lives in the detection observer so it shares the collector's single connection and cycle cadence.

## Consequences

- Throughput alerts no longer describe the traffic schedule: the v0.5 smoke saw none in ten minutes with four iperf3 rounds and two `loss` faults, with at most one alert open at a time. `loss` faults, which only show as throughput deviations (ADR 0008), are now below the floor at 20 % loss on a 1 to 8 Mbit/s flow; raising the fault loss or lowering `min_bps_delta` brings them back.
- Confirmation delays every open by `open_after_signals - 1` cycles: a `drop_rate` alert opens 16 to 18 s after a `host_down` fault starts instead of within one poll, and still resolves about 65 s after the fault clears (60 s policy plus one cycle). `opened_at` points at the first signal, so the row still dates the anomaly correctly; only the notification is later.
- The feed is gapless by construction, at the cost of serializing alert writers through one advisory lock. Writers are the collector cycle and acknowledgements, so contention is negligible; a second collector writing the same table would be serialized too.
- An open alert is refreshed, and its `seq` bumped, on every cycle it stays signalled, so the WebSocket sends an `alerts` frame every 5 s while an alert is open, carrying the latest value and z-score. Limiting the bump to severity or value changes would cut the traffic and is a follow-up.
- The broadcaster reads at most 500 changed rows per cycle; more than 500 open alerts changing in one cycle lag by a cycle, which is far above the demo fleet.
- Baselines cost 32 upserts per cycle on the demo fleet; the table holds one row per port metric, never grows, and a restart logs `loaded 32 baselines` and resumes scoring with no warm-up gap. A baseline persisted during an anomaly is reloaded as such, which is the intended behaviour: the alert reopens from the table and the baseline keeps absorbing the level.
- Alerts of ports that vanished while the collector was down, or that belong to an older database volume, are resolved and notified at startup once the prune window passes; the smoke saw three stale v0.4 alerts resolve this way. That is correct for the alerts and the right thing for routes, but a restart with a changed topology produces a burst of `resolved` events.
- Retention runs inside the detection observer, so it is inactive when `NETPULSE_COLLECTOR_DETECTION_ENABLED` is `false`; a collector that only writes samples does not purge old alerts either.
- A switch-side `loss` fault that the drop counters would see was not pursued: Open vSwitch does not count packets dropped by a flow with no action or by a meter in the port counters either, so it would not move `drop_rate`. `host_down` remains the only fault visible as drops.
- Multi-metric and multi-port correlation, silence windows and alert annotations remain out of scope.
