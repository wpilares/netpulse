# ADR 0008: Anomaly detection, alert lifecycle and fault injection

- Status: Accepted
- Date: 2026-10-26

## Context

v0.3 computes per-port KPIs (ADR 0007) but nothing judges them: there is no notion of what a port normally does, no alert, nowhere to store one, and the emulated network never fails, so a detector would have nothing to find. v0.4 needs a baseline per port and metric, a rule that turns a deviation into an alert with a severity, storage that survives restarts and supports acknowledgement, a live feed into the dashboard, an outbound notification hook, and faults in the Mininet network that produce real anomalies in the OpenFlow counters.

Three placement questions shaped the design: where detection runs (collector, API or database), where alert state lives (hypertable, plain table or memory), and how the API learns about new alerts without the collector and the API talking to each other.

## Decision

**Baseline and scoring live in `packages/core`** (`netpulse_core.anomaly`), as pure functions over the KPI points from ADR 0007. Each `(dpid, port_no, metric)` keeps an exponentially weighted mean and variance (`alpha` 0.2); a value is scored only once the baseline has seen `warmup_samples` (12, one minute at 5 s polling) and is folded into the baseline afterwards, so an anomalous sample still moves the mean. The z-score divides the deviation by the larger of the EWMA standard deviation and a floor (`10 kbit/s` for throughput, `0.005` for rates), so a perfectly flat series cannot produce infinite scores. Severity is `warning` at `|z| >= 3` and `critical` at `|z| >= 5`, with absolute guards per metric kind: throughput deviations under `min_bps_delta` (100 kbit/s) are ignored whatever their z-score, while `drop_rate >= 0.02` and `error_rate > 0` are at least `warning` whatever the baseline says. Counter resets skip scoring and leave the baseline untouched. Metrics: `rx_bps`, `tx_bps`, `drop_rate`, `error_rate`.

**Drop and error rates count attempted frames.** `drop_rate = Δdropped / (Δpackets + Δdropped)` and likewise for errors, over rx and tx together. A port whose peer is down counts every frame in `tx_dropped` while `tx_packets` stays frozen; dividing by delivered packets gave `null` for exactly the case the detector exists for. Against attempted frames a port that only drops reports `1.0`.

**Alert lifecycle lives in `netpulse_core.alerts`** as a pure `evaluate_alerts(states, signals, now, policy)` step. There is one open alert per key: a repeated signal refreshes `last_seen_at` and the observed values and escalates the severity when the signal is stronger (severity never drops while open); an alert with no signal for `resolve_after_seconds` (60 s) resolves; a signal that arrives inside `cooldown_seconds` (120 s) after resolution is suppressed; after the cooldown the state is forgotten and the next signal opens a new alert. Acknowledgement is a user mark stored on the row and does not take part in the lifecycle.

**Detection runs in the collector**, not in the API or in SQL. The collector already holds consecutive reports on the write path, so it can score every poll without a second reader of the hypertable, and alerts are facts produced once and persisted; the API only reads them. `AnomalyDetector` keeps the previous sample, the baselines and the alert states in memory, prunes ports absent for 60 cycles, and `DetectionObserver` applies the resulting events through an `AlertRepository` port and an `AlertNotifier` port. A failed write is logged and the notifier still runs; the next cycle re-signals a still-active anomaly.

**Alerts are a plain table**, not a hypertable: rows are updated in place (refresh, escalate, resolve, acknowledge) and the volume is tiny compared to samples. Identity `id`, the same `dpid`/`port_no` types and range checks as `port_stats`, check constraints on `metric`, `severity`, `status` and on `resolved_at` matching `status`, a partial unique index on `(dpid, port_no, metric) WHERE status = 'open'` and an index on `(status, opened_at DESC)` for the list endpoint. An `opened` event is an upsert on the partial index, so a retried cycle or a collector restart that re-opens an alert already in the table refreshes the row instead of failing. At startup the collector seeds its states from the open rows, so a still-active anomaly keeps refreshing the same alert and a vanished one is resolved after the policy window.

**The API streams alerts with a cursor and a per-subscriber snapshot.** Every live cycle the broadcaster fetches rows with `updated_at` after its cursor (all open alerts on the first cycle), remembers which alerts are open and emits one `alerts` frame carrying only the changed rows. A new WebSocket subscriber receives the open-alert snapshot right after `hello` when any alert is open, so a client that connects between changes starts from the full state, and `GET /api/v1/alerts` serves the same rows over REST for the initial render and for history (`status` `open`, `resolved` or `all`). `POST /api/v1/alerts/{id}/ack` sets `acknowledged_at` once and returns the row; repeated calls keep the first timestamp and an unknown id is `404`. The collector and the API never talk to each other: the table is the contract.

**Notifier behind a port.** `LoggingAlertNotifier` is the default; when `NETPULSE_COLLECTOR_ALERT_WEBHOOK_URL` is set, `WebhookAlertNotifier` POSTs every batch of events as JSON (`{"events": [{"kind", "alert": {...}}]}`, where `alert` carries the same fields as the REST representation minus `id` and `acknowledged_at`, and `dpid` is a JSON number). Failures are logged without the URL, and httpx2's request logging is quieted so the URL never reaches the logs through a third party.

**Fault injection produces real counter anomalies.** The network schedules one fault every `NETPULSE_NETWORK_FAULT_PERIOD_SECONDS` (90 s) lasting `NETPULSE_NETWORK_FAULT_DURATION_SECONDS` (30 s), on a deterministic cycle that visits every host link first and then the switch-to-switch links, alternating two kinds:

- `loss` adds `NETPULSE_NETWORK_FAULT_LOSS_PERCENT` (20 %) `netem` packet loss on both ends of the link while keeping the `TCLink` shaping. `netem` discards packets inside the Linux queue discipline, after the switch has already counted them as transmitted, so Open vSwitch never reports them as drops; the fault is visible to the detector as a throughput deviation (`rx_bps`, `tx_bps`) on the receiving side, which is what the first smoke run showed.
- `host_down` takes the host-side interface of a host link down. The switch port stays up and LLDP keeps the topology intact, but the veth driver counts every frame sent towards the dead peer in that switch port's `tx_dropped`. A dead peer attracts almost no traffic on its own, so another host (a sibling behind the same switch when there is one) pins the downed host's MAC as a permanent neighbour entry and floods it with `ping -f` for the fault duration, which gives the switch port thousands of attempted frames; with the attempted-frames denominator above, `drop_rate` reaches `1.0` and a `critical` alert opens within one poll. The probe forgets the neighbour entry when the fault clears. Switch-to-switch links only ever receive `loss`, since a host must stay behind a `host_down` fault.

The period counts from the moment the previous fault clears, so faults repeat every 120 s of wall clock (30 s fault plus 90 s gap), which leaves the baselines time to recover between them. Injection is on by default so the demo fires and `NETPULSE_NETWORK_FAULT_ENABLED=false` disables it; an active fault is cleared on shutdown.

## Consequences

- One tested function owns the detection semantics and one owns the lifecycle; the collector, the tests and a future offline replay share them. Alpha, warm-up, the z thresholds and the lifecycle windows are settings (`NETPULSE_COLLECTOR_DETECTION_*`, `NETPULSE_COLLECTOR_ALERT_*`); the absolute floors are `DetectionConfig` defaults until tuning shows they need to move.
- The EWMA adapts: a sustained step in throughput is absorbed within a few samples, so throughput alerts describe changes rather than levels and resolve on their own even if the new level persists. That is the intended behaviour for `loss` faults, but it also means the iperf3 schedule itself, whose flows start and stop every 15 s with rates between 1 and 8 Mbit/s, opens short `rx_bps`/`tx_bps` alerts with the default thresholds. They resolve within about a minute and are visible noise in the demo; tuning `min_bps_delta` and the z thresholds, or a seasonal baseline, is a follow-up. Rate alerts do not have this problem because the absolute floors keep them open for as long as the port keeps dropping.
- Baselines live in collector memory. A restart re-enters warm-up (about a minute) before scoring resumes; open alerts survive because they are reloaded from the table, but their baselines do not, so an anomaly still active after a restart is re-detected only once the baseline has settled on the anomalous level or the signal changes again. Persisting baselines is deferred.
- The `updated_at` cursor uses `now()`, which PostgreSQL fixes at transaction start. A row committed after the API's poll but stamped earlier than the cursor is skipped by the live feed until its next change; the window is milliseconds and the per-subscriber snapshot plus `GET /api/v1/alerts` cover a reconnect, but a strictly gapless feed would need a monotonic sequence instead of a timestamp.
- `netem` loss stays invisible to OpenFlow port counters by construction; the detector sees it indirectly, through throughput. A fault kind that the switch counts as drops is `host_down`, and the probe exists only because the demo topology carries too little background traffic towards a silent host. Real networks would not need it.
- Alerts are per port and per metric with no correlation: a `host_down` fault opens a `drop_rate` alert on the switch port and, as the flows die, throughput alerts on the ports along the path. Multi-metric and multi-port correlation, alert routing and silencing are out of scope for v0.4.
- The alerts table grows with every resolved alert and has no retention policy yet; at demo rates that is a few hundred rows per hour.
